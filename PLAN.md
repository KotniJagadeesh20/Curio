# Creator Publishing Platform: Build Plan

Evolve the existing AlgoQuest app (admin-managed learning content) into a **creator-driven knowledge & experience publishing platform**.

> Principle: every creator owns their content. The platform provides the tools to create, organize, publish and discover it. Admin governs the platform; admin does not own everyone's content.

How we work: **one step at a time.** Each step is small, ends in something runnable, and has a "Done when" checklist. We finish and verify a step before starting the next. Tick the boxes as we go.

## 2. Where we're going

```
Creator (User + UserProfile @username)
 └─ Collection   (was Track)    title, description, cover, category, visibility, status
     └─ Module   (was Section)  groups pages
         └─ Page (was Lesson)   title, summary, blocks[]
              └─ Blocks         heading · text · code · image · video · html · svg · callout · divider · (later) table, file, embed
```

Three experiences, kept separate:
- **Public**: discover, read collections/pages, creator profiles, share links.
- **Creator workspace**: any logged-in user: My Collections, editor, drafts, publish, profile settings.
- **Admin**: users, categories, moderation. Never required in order to publish.

Out of scope for now: DSA/practice, progress dashboard, AI tutor, comments, likes, follows, bookmarks, payments, recommendations.

## 3. Key decisions (please confirm or change before Step 1)

1. **Evolve tables in place, don't create parallel ones.** Add columns to `tracks/sections/lessons` and keep the table names. Rename only in the API, DTOs and UI (Collection / Module / Page). Java entities can be renamed later with `@Table(name=...)`. This avoids copying data between tables and keeps the seeded content working. *(The spec suggested new tables plus migration; in-place is lower-risk for a working MVP.)*
2. **Keep the flat block JSON format** (`{type, ...fields}`), not the spec's `{type, data:{...}}`. The editor, renderer and stored data already use it. Add server-side validation instead of changing the shape.
3. **Status model:** `status` = `DRAFT | PUBLISHED | UNLISTED` (set by the creator), plus a separate `moderation_status` = `OK | HIDDEN` (set by admin). Replaces the `published` boolean. A collection is publicly visible only if `PUBLISHED` (or `UNLISTED` via direct link) **and** `moderation_status = OK`.
4. **Direct publishing, no approval queue.** Admin can hide content and suspend accounts.
5. **Existing seeded content** is assigned to the admin user as owner, in a collection under a "Programming" category.
6. **Slug scope:** unique per creator (`/@username/collection-slug`), not global.
7. **Media:** start with URL-based images; real uploads come in Phase 3 behind a `MediaStorage` interface. Local disk is for dev only; production uses S3-compatible storage (see 3a).
8. **Legacy lesson fields** (`concept`, `common_mistakes`…) stay in the DB for now. Pages without `blocks` keep rendering as before. We drop them only after a later conversion step.

### 3a. Clarifications added after review (rules the steps below must follow)

**Publishing rules (collection vs page)**
- Collection `status` = `DRAFT | PUBLISHED | UNLISTED`. Page `status` = `DRAFT | PUBLISHED` only (a page is never unlisted on its own).
- A page is publicly readable only if **page = PUBLISHED**, **parent collection ∈ {PUBLISHED, UNLISTED}**, `moderation_status = OK`, the collection is not soft-deleted, and the owner is `ACTIVE`.
- `UNLISTED` collections open by direct link but never appear in discover, search or profile lists.
- Publishing a collection does **not** auto-publish its draft pages. Draft pages stay hidden, and the editor shows "N draft pages not visible".
- Publishing requires: a title, and at least one PUBLISHED page.
- Module has no status of its own: it is visible iff it has at least one publicly readable page.

**Suspended users:** cannot log in, and their token stops authenticating (so create/edit/publish/upload all fail with 401). Their public profile and all their content return 404 while suspended. Reactivating restores everything. Nothing is deleted.

**Ownership & moderation:** `owner_id` is set once at creation, is never accepted from a request body, and no endpoint changes it. Admin moderation only touches `moderation_status` (and writes an audit row). Every nested operation (module, page, reorder, media) resolves the **root collection's owner** and checks it. A non-owner gets 404 for drafts and 403 for visible content they can't edit.

**Deletion:** collections are **soft-deleted** (`deleted_at`, hidden everywhere, recoverable by the owner for 30 days, then purged by a scheduled job). Modules and pages are hard-deleted behind a confirm dialog (they are cheap to recreate and live inside a soft-deletable collection). Because `UNIQUE(owner_id, slug)` can't be partial on H2, soft delete **renames the slug** to `slug~deleted~<id>` so the slug is reusable. Media files are not deleted when content is deleted; the purge job removes unreferenced assets later.

**Usernames are immutable (for now):** they appear in public URLs (`/@username/collection/page`), so changing one would silently break every shared link. No endpoint changes them. If renaming is ever added, it must come with a `username_history` redirect table and a cool-down; that is out of scope until then.

**Profile visibility is independent of collection visibility:** `PRIVATE` hides only the profile page `/@username` and its entry in creator lists. It does **not** change whether the creator's PUBLISHED collections are listed or readable, and a collection's status never changes the profile's visibility. Step 6 must keep these as two separate checks (the collection response may show the creator's username and display name either way), and the Step 6 tests must cover a PRIVATE profile with a PUBLISHED collection.

**Protected seeded admin:** the account created by `AdminSeeder` (`users.protected_account = true`) can't be demoted, suspended or deleted through user-management endpoints. Every such endpoint must call `UserGuard.requireNotProtected`. (Changing it requires direct database access, deliberately.)

**Profile is extensible:** `user_profiles` gets `banner_url`, `interests` (JSON), `featured_collection_id` and `visibility` columns up front, but Step 1's API only uses display name, bio, avatar, banner and social links. The rest is wired in Phase 4.

**Templates are data, not code:** a template is a JSON structure `{ name, category, modules: [{ title, pages: [{ title, blocks: [...] }] }] }` stored in the repo (later possibly a table). "Use template" just calls the normal create-collection/module/page APIs. There is exactly one editor and one renderer. Initial templates: Blank, Programming Tutorial (Introduction, Prerequisites, Concepts, Examples, Practical Implementation, Summary), Travel Guide (Overview, How to Reach, Places to Visit, Accommodation, Food, Travel Tips), Recipe, Personal Experience.

**Security checklist (applies to every step that touches it):** ownership on every nested route; suspended users blocked; HTML in a sandboxed iframe without `allow-same-origin`; SVG sanitized server-side and rendered via `<img>` or sanitized inline; only `https` (or app-relative) URLs for image/video/embed; uploads checked by size, extension **and** magic bytes; admin moderation cannot change `owner_id`.

**Media storage:** `MediaStorage` interface with a `LocalDiskMediaStorage` (dev/test only) and an `S3MediaStorage` (production). Production must use persistent object storage, because local disk is lost on ephemeral hosting. The storage key lives in the DB, never the bytes.

**Database policy (decided 2026-11-02): develop and test on H2; PostgreSQL verification is a pending production-readiness task.** Docker/PostgreSQL are not available in the development environment, so:
1. All development and automated integration tests run on H2 (`@ActiveProfiles("h2")`).
2. Migrations and repository queries stay PostgreSQL-compatible: plain standard SQL (`BIGSERIAL`, `VARCHAR`, `TEXT`, `TIMESTAMP WITH TIME ZONE`, `BOOLEAN`), JPQL or derived queries, no `MODE=PostgreSQL`-only tricks relied on, no native queries unless unavoidable, and no H2-specific SQL or functions.
3. No step is blocked by PostgreSQL being unavailable, and the architecture is not bent to suit H2.
4. The real-PostgreSQL run is tracked in the **Production-readiness backlog** (end of this file) and as the Step 20 gate. Until then every migration after V9 counts as "H2-verified only".
5. `V9MigrationPostgresTest` and the commands under Step 1 are ready for when a Postgres is available again (it is skipped automatically without `PG_TEST_URL`).

### 3b. Conflicts with the existing architecture (found by reading the code)

1. **Admin owner doesn't exist when migrations run.** The admin user is created by `AdminSeeder` at app start, *after* Flyway. On a fresh DB a migration can't set `owner_id = admin`. **Resolution:** `owner_id` is nullable in SQL and `optional=false` on the entity. `AdminSeeder` creates the admin, then assigns all `owner_id IS NULL` content to it (idempotent). A startup check logs an error if orphans remain. Step 3 will make the column `NOT NULL` only once a non-seeder path guarantees it (decision to revisit in Step 19).
2. **`AdminContentController` lets admin edit everything**, which contradicts "admin does not edit other creators' content." **Resolution:** the creator API (Step 5) is the only write path for tracks/sections/lessons. Admin edits seeded content as its owner through it. The admin track/lesson endpoints and `AdminTracks.tsx` are removed in Step 8, once the creator UI replaces them. Admin problems/users endpoints stay.
3. **`JwtAuthFilter` has no status check, and `/api/auth/login` doesn't either.** Suspension needs a check in both places (Step 1).
4. **`SecurityConfig` makes everything outside `/api/auth`, `/api/tracks|lessons|problems` GET and `/api/admin` require auth,** so the new `/api/public/**` needs an explicit `permitAll` GET rule.
5. **React Router 6.30 does not support `/@:username`** (dynamic segments must be a whole path segment). **Resolution:** route `/:handle/*` placed after all static routes, and the component renders NotFound unless `handle` starts with `@`. Reserved usernames are still blocked server-side.
6. **Existing tests and the frontend sign up with only name, email and password.** `username` must therefore be optional at signup (derived from the email), or all of them break.
7. **`orphanRemoval` + `cascade ALL` on Track→Section→Lesson** conflicts with soft delete if applied to children. Soft delete is on the collection row only; children are untouched.
8. **`users` rows are cascade-deleted by FKs today** (`lesson_progress`, `comments`). New `owner_id` FKs use `ON DELETE RESTRICT`: users are suspended, not deleted, so content can't vanish with an account.
9. **No Testcontainers in `pom.xml`, and Docker was not running last session.** Real-Postgres testing needs Docker or a locally installed Postgres (Step 20).

**Step 9 data-integrity follow-up: malformed stored blocks (DONE)**
Problem: `readBlocks` turned unparseable stored JSON into `[]`, so `GET /api/pages/{id}` showed an ordinary empty page and a Save could overwrite the original content. Fixed without a migration and without touching publishing, ownership or visibility rules.

*How malformed content is handled now*
- **Three states, never confused.** Stored `blocks` is (1) SQL `NULL` = legacy page (`legacy: true`, `blocks: null`, `legacyContent` filled); (2) a **valid array**, possibly empty = a readable page (`blocks: []` is a genuinely empty page); (3) **unreadable** = `blocksUnreadable: true`, `blocks: null`, `legacy: false`, `legacyContent: null`. Unreadable means: not JSON (including empty/blank text), JSON followed by junk, JSON that is not an array (`null`, object, string), or an array containing an item that is not an object with a non-blank string `type` (the same rule the server enforces on write).
- **Reading never alters it and never reports `[]`** (`PageDto.blocksUnreadable`, new response field). `hasContent` is `true` for it (never "empty").
- **Title, summary (and slug where allowed) can still be saved.** A request without `blocks` leaves the stored body byte-for-byte as it was.
- **A block replacement is refused with `409 Conflict`** ("This page's saved content can't be read, so it was not replaced...") and the whole request is rolled back: title, summary and the stored body are all unchanged. This applies to `[]` as much as to real blocks.
- **Explicit recovery:** `PageUpdate.discardUnreadableContent: true`, valid only together with `blocks` and only while the stored content is unreadable. Otherwise `400` (flag with readable or legacy content: "nothing to discard"; flag without `blocks`). An explicit `false` behaves like omitting it. The old body is gone after a recovery, by design and by explicit request.
- Publish, unpublish, reorder, the collection outline and ownership checks work on such a page without touching the body; a non-owner (including an admin) cannot discard (404 for a draft, 403 for published, DB unchanged).
- **Frontend:** the editor shows an alert ("kept exactly as it is and can't be edited here; you can still edit the title and summary"), **hides the block editor** (an empty editor would look like a blank page), sends **no `blocks`** on Save, and never calls the page empty when publishing. "Discard it and start over" opens a confirmation ("cannot be recovered"); after confirming nothing is sent until Save; the Save then carries `blocks` **and** `discardUnreadableContent: true`; "Keep the unreadable content" backs out; a server 409 is shown and nothing is marked saved. After a recovery the page is an ordinary one (no flag on later saves). The editor's own check for items it can't read (`unreadable > 0`) stays as a second layer and locks the body the same way (no recovery button, because the server then considers the content readable).

**Formats and pipeline (12a)**
- Accepted: JPEG, PNG, WebP (lossy, lossless, and alpha variants **only after each is proven by a fixture test**; anything the reader can't decode is rejected as `MEDIA_TYPE_UNSUPPORTED`). JPEG uses the JDK reader; CMYK/YCCK and other unconvertible colour spaces are rejected as `MEDIA_COLORSPACE_UNSUPPORTED`. Rejected: SVG (stays a sanitised `svg` block), GIF, AVIF, HEIC, **animated WebP** (RIFF `VP8X` animation flag / `ANIM`/`ANMF` chunk) and, for consistency, **animated PNG** (`acTL` before `IDAT`).
- Dependency: `com.twelvemonkeys.imageio:imageio-webp` (read-only plugin, which is enough because we re-encode). Maven Central lists 3.15.3 as latest (checked 2026-11-06). **Before adding it, 12a verifies:** the exact version, Java 17 compatibility, that the plugin is found when running from the packaged Spring Boot jar (not only from tests; ImageIO SPI registration), and the fixture matrix above. Pin the version. `ImageIO.setUseCache(false)`.
- Steps, in order, with nothing persisted until all pass: (1) servlet multipart limit and a counting stream cap, (2) exactly one part named `file`, (3) magic-byte sniff, declared type and extension must agree with it, client MIME never trusted, (4) pick the reader **by sniffed format** (not by guessing), (5) animated-image check, (6) read only the header for width/height, (7) safe size math, (8) bounded decode, (9) re-encode, (10) thumbnail.
- Safe size math: dimensions are `int` from the header, rejected if <= 0 or > 20 000 per side; pixels and the decode-memory estimate are computed in `long` with `Math.multiplyExact`; reject above `media.max-pixels` (25 000 000) **before** any raster is allocated. Large images are decoded with source subsampling to about <= 2560 px on the long edge so a 25 MP file never allocates a full-size raster.
- Memory-bounded concurrency: a semaphore counted in **estimated MB of raster** (not request count), budget `media.decode-budget-mb` (default 256, startup refuses a budget above 25% of max heap). Waiting too long returns 503 `MEDIA_BUSY`.
- Output: orientation applied, then re-encoded: PNG when there is alpha, otherwise JPEG q85; original capped at 2560 px long edge; one thumbnail variant at 640 px long edge. Stored `content_type` is the **canonical output type** (`image/jpeg` or `image/png`), never the client's. No filename is stored (no library in v1).
- *Honest limit:* re-encoding strips metadata (EXIF/GPS, ICC, XMP) and appended data from the stored copy. It does not prove the decoder was safe. Decoders are an attack surface: mitigated by header-first bounds, the memory budget, a pinned and updated dependency, generic error messages, and no stack traces to clients. There is no hard CPU timeout (ImageIO decode isn't interruptible) and no out-of-process decoding in v1.
- Limits at both layers: `spring.servlet.multipart.max-file-size` and `max-request-size` come from `media.max-bytes` (+ small overhead) so an oversized body is refused before the controller (mapped to 413 `MEDIA_TOO_LARGE`); the application also counts actual bytes read.
- Error codes (stable, no internals): `MEDIA_TOO_LARGE`, `MEDIA_TYPE_UNSUPPORTED`, `MEDIA_CORRUPT`, `MEDIA_ANIMATED`, `MEDIA_DIMENSIONS`, `MEDIA_COLORSPACE_UNSUPPORTED`, `MEDIA_QUOTA`, `MEDIA_BUSY`, `MEDIA_IN_USE`, `MEDIA_NOT_READY`. Suspended users get 401, like every other creator endpoint (`CurrentUser.require()`: the reason is not revealed).

**Schema, V13 (additive only; V1-V12 untouched)**
- `media_assets`: `id UUID PK` (app-generated), `owner_id BIGINT NOT NULL FK users`, `status` (`UPLOADING | READY | DELETING`), `content_type`, `width`, `height`, `size_bytes`, `sha256`, `thumb_width`, `thumb_height`, `thumb_size_bytes`, `thumb_sha256`, `created_at`, `ready_at`, `unreferenced_since NULL`, `delete_attempts INT NOT NULL DEFAULT 0`. Indexes: `(owner_id)`, `(status, unreferenced_since)`. `size_bytes`, `sha256` describe the **actual stored output** of each variant.
- `media_references(asset_id FK media_assets, page_id FK lessons ON DELETE CASCADE, PK(asset_id, page_id))`: **page-block references only**, one row per asset-page pair however many times the image appears on the page. `asset_id` FK is RESTRICT (safety net: a referenced row can't be deleted).
- `tracks.cover_asset_id UUID NULL FK media_assets` (RESTRICT): **the single source of truth for collection covers**. Legacy `cover_url` stays. No `COVER` rows in `media_references`.
- "Referenced" always means: a `media_references` row **or** any `tracks.cover_asset_id` (including soft-deleted collections, so restore works). Delete checks, orphan cleanup and quota "in use" logic all use that one definition (one repository method).
- Permanent removal (the later 30-day purge, Step 20) cascades page references at the DB level; the sweeper's stamp-first rule (below) handles the resulting orphans.
- Dropped from the first draft: `display_name`, the list endpoint, the `COVER` reference kind.

**Lifecycle**
- `UPLOADING` (row reserved, objects being written) -> `READY` (served, referenceable) -> `DELETING` (unusable, being removed; the row is deleted once storage deletion succeeds).
- Upload flow (DB and storage can't be atomic, so the DB row is written **first** and always names the objects):
  1. Validate and process fully (nothing persisted yet). A cheap non-atomic quota pre-check avoids wasting CPU.
  2. Reservation tx: lock the owner's `users` row (`PESSIMISTIC_WRITE`), apply the quota rule below, insert the `UPLOADING` row, commit. Two simultaneous uploads cannot both pass on the same old total.
  3. Put original, then thumbnail.
  4. Tx: set `READY`, `ready_at`, `unreferenced_since = now()`.
  - Any failure in 3/4 (a handled error, not a crash): best-effort delete of both keys, then mark `DELETING`; the sweeper finishes whatever is left.

*Quota accounting (one rule, one place):*
- Byte usage = `size_bytes + thumb_size_bytes` of each asset, i.e. the **actual stored output** (never the uploaded size). Asset count = number of rows.
- `UPLOADING`, `READY` and `DELETING` rows **all count against both quotas** (bytes and count). An asset stops counting only when its **database row is deleted, and the row is deleted only after both storage objects are confirmed gone**. So concurrent uploads, a stuck upload, or repeated failed deletions can never let a user exceed the quota.
- Every operation that reserves quota (the reservation tx) or releases it (the final row delete after storage cleanup, by the sweeper or inline by `DELETE`) takes the owner's `users` row lock first and follows the same order (`users` row, then asset rows). The advisory pre-check before processing is not authoritative and never reserves anything.

*Crash recovery (the row is written first and names its objects through the id-derived keys, so every case is recoverable from the DB alone; every sweeper step is idempotent and safe to repeat):*

| Crash point | State left behind | Recovery |
|---|---|---|
| Before either object is stored (before the reservation commit, or just after it) | Before the commit: nothing persisted. After it: an `UPLOADING` row, no objects | The row counts against quota until the sweeper sees it older than `media.upload-timeout` (30 min) and marks it `DELETING`; deleting the two keys is a no-op (a missing object is success), then the row is removed. |
| After the original is stored, before the thumbnail | `UPLOADING` row, original object only | Same path: the timeout sweep marks `DELETING`, deletes both keys (the thumbnail one is absent, which is fine), removes the row. Never served: only `READY` assets are served. |
| After both objects are stored, before `READY` | `UPLOADING` row, both objects | Same path. The upload is discarded rather than completed (the client never got its 201, which is sent only after `READY` commits), so it can never become referenceable; the client re-uploads. |
| During deletion of either object | `DELETING` row, zero, one or both objects remain | Every sweep retries all `DELETING` rows: delete both keys (idempotent), then delete the row. A storage error bumps `delete_attempts` and leaves the row for the next pass; the row keeps counting against quota the whole time. High `delete_attempts` is logged for an operator. A crash between the second object delete and the row delete just repeats harmless deletes on the next pass. |

- The sweeper only ever moves a row forward (`UPLOADING -> DELETING -> removed`, `READY -> DELETING` when unreferenced); it never resurrects. Two overlapping runs, or a restart mid-run, can't corrupt anything because each transition re-checks the row under its lock.
- **Sweeper** (`@Scheduled`, `media.sweep-interval` default 10 min, single-instance assumption documented): (a) `UPLOADING` older than `media.upload-timeout` (30 min) -> `DELETING`; (b) `READY`, unreferenced, `unreferenced_since` older than 24 h -> `DELETING`; (c) a `READY` unreferenced asset whose `unreferenced_since` is NULL (references removed by a cascade) first gets stamped, and is purged on a later pass; (d) every `DELETING` row: delete the storage objects (idempotent), then the row; on failure bump `delete_attempts` and retry next pass (alert threshold logged).
- **Race-free marking:** lock the asset row `FOR UPDATE`, then re-check "referenced" in a **separate statement** (READ COMMITTED), then set `DELETING`. Never a single-statement compare-and-set with a `NOT EXISTS` subquery (its snapshot can miss a reference committed while it waited for the row lock).
- `unreferenced_since`: set at `READY`, set again whenever the last reference is removed, cleared when a reference is added. It is only a grace clock; the sweeper always re-verifies the real references, so a stale value can never delete a referenced asset.

**References, validation, projection (12b)**
- Image block: `{id, type:"image", assetId?, url?, caption?}`. Exactly one source: `assetId` (canonical UUID) **or** a legacy https/site-relative `url`; `assetId` together with a non-empty `url` is refused on write (`INVALID_BLOCKS`, field `assetId`). `html` blocks can't use assets (CSP allows only `data:` images).
- **Responsibilities stay separate:** `BlockValidator` stays pure: it gets a pre-fetched map of the writer's candidate assets (one `findAllById`, no per-image queries) and checks that each `assetId` exists, belongs to the collection owner and is `READY`. `BlockSanitizer` keeps sanitising and projecting untrusted data (it passes a UUID-format `assetId` through and does no lookups). A separate `MediaUrlResolver` runs when the response is built: one query for all asset ids in the page (or in the list of collections), then fills in `url`, `width`, `height`. A block whose asset is missing, not `READY` or not owned by the collection owner is omitted like any other bad block. The legacy `ContentService` path has no assets (admin-authored, URL only).
- **Reference replacement** happens in the existing page-save transaction (after the page row lock): extract asset ids from the saved body -> lock those asset rows **in ascending id order** -> validate -> diff against existing `media_references` -> insert/delete -> stamp or clear `unreferenced_since`. Cover changes follow the same order (old and new asset together, sorted). Page row lock -> sorted asset locks is the only order used anywhere; deletion takes just the asset lock, so no cycle. Metadata-only saves never validate or touch the body or its references. Autosaves of drafts count as references. Page, module and collection deletes go through one `MediaReferenceService` method that stamps the freed assets.
- **Cover contract:** `coverAssetId` and legacy `coverUrl` must not both be explicitly supplied (400); omitted fields preserve what is stored; supplying one clears the other; `""` still clears the legacy URL; `coverAssetId: null` clears the asset cover. The public DTO's `coverUrl` is the resolved asset URL (else the legacy URL); a nullable `coverThumbUrl` is added for cards.
- **Public serving rule** (reuses `Visibility`, no second definition): `GET /api/public/media/{id}` and `/{id}/thumb` serve an asset only if it is `READY` and at least one reference is genuinely readable: a **page** reference where the page is `PUBLISHED` in a collection that is `PUBLISHED`/`UNLISTED`, moderation `OK`, not soft-deleted, owner not suspended, with module and page linked correctly; or a **cover** on a collection that is publicly readable by `Visibility.collectionReadable` (including having a published page). Anything else is the same 404 as unknown (existence not revealed). Public visibility is per asset: an image shared by a public page and a draft stays public, and the draft's text is never exposed; a draft-only image stays private. `UNLISTED` media works by direct link only, since IDs are unguessable random UUIDs and no list exposes them. Implementation: one SQL `EXISTS` mirroring `Visibility` (the precedent for list queries) **plus a parity test** that runs the full status/moderation/deleted/owner/published-page matrix through both and fails on any difference (matrix listed under *Final decisions confirmed*).
- **Owner serving:** `GET /api/media/{id}/content[?variant=thumb]`, authenticated, active owner only; non-owner, admin and unknown ids all get 404 (admins get no creator access; moderation arrives in Step 18). 12a ships this route only; 12b adds the public route.
- **Caching/headers:** public: `Cache-Control: public, max-age=60` (`media.public-max-age`), strong `ETag` = the stored variant's sha256, conditional `If-None-Match` supported with **weak comparison** (RFC 9110; see the 12b implementation plan) but **visibility is checked first**, so a revoked asset answers 404, never 304. Revocation can lag up to the max-age in browsers/shared caches (documented). Owner route: `private, no-store`, no ETag. Always: canonical `Content-Type`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Content-Length`, no `Content-Disposition` filename. `immutable` and CDN caching are deferred until there is an invalidation or versioned-URL strategy.
- **Delete:** `DELETE /api/media/{id}` (12b), owner only. Referenced (page or cover, including soft-deleted collections) -> 409 `MEDIA_IN_USE` with up to 20 usages (`kind`, collection/page ids and titles, `inTrash`) and the total count; `UPLOADING` -> 409 `MEDIA_NOT_READY`; otherwise lock, re-check, mark `DELETING`, commit, attempt storage removal inline, return 204 (retries are the sweeper's job; `DELETING` repeats are 204). No frontend delete UI in v1: it exists to discard an unused upload.

**12b implementation plan (FINAL CLARIFICATIONS 2026-11-09, second review round; AUTHORIZED 2026-11-09 and implemented as below, see "12b as built"; V13 unchanged; 12c and 12d untouched)**

*Starting point (verified in code):* V13 already holds `media_references`, `tracks.cover_asset_id` and `unreferenced_since`, so there is no media migration (V14 stays reserved for `reports`). `BlockRules` rejects `assetId` today, so no page can reference an asset yet and no backfill is needed. Page bodies are written only by `CollectionService.createPage` and `updatePage`. `MediaSweeper` already handles stale `UPLOADING` and `DELETING` rows; 12b adds the orphan steps. No hard delete of collections exists yet (Step 20 purge).

*Lock hierarchy (the only order used anywhere):* `users` (quota reserve/release only) -> **collection (`tracks`) row -> module row -> page rows (ascending id) -> asset rows (ascending UUID)**. No path acquires a lower level and then a higher one. Every lock is a fresh `FOR UPDATE` read (`em.refresh(..., PESSIMISTIC_WRITE)` or a lock query that is the first load of that row in the transaction), never a cached entity, because a JPQL lock query returns an already-loaded entity with stale fields.

*Rule that makes a write impossible underneath a parent that is being deleted:* every operation that creates, changes or deletes pages, modules, covers or the collection itself **takes the collection row lock first and re-reads `deleted_at` under it** (404 if the collection is soft-deleted, except `restore`). Today these operations check ownership and deletion at the start of the transaction without locking the collection, so a soft delete can commit between the check and the write; 12b closes that for the operations below. The cost is that writes within one collection run one after another (a single owner, v1: acceptable). `publish`, `unpublish` and `reorder` do not touch media or references and keep their current page-level locking (a note for Step 20, whose purge will also lock the collection first).

| Operation | Lock order | Serialisation against a parent being deleted |
|---|---|---|
| Page save (`updatePage`) | collection (re-check not deleted) -> page (`lockFresh`) -> read existing refs -> union of existing and incoming assets, sorted | Module delete or purge holds collection (or module) and all its pages first, so the save waits; afterwards the page is gone: `lockFresh` maps it to 404. If the save won, the delete locks the page afterwards and collects its candidate assets **after** the locks, so they include the new references. Soft delete holds the collection lock, so the save waits and then gets 404. |
| Page create (`createPage`) | collection (re-check) -> module and its pages (`lockSiblings`) -> insert page, flush -> assets sorted | A concurrent module delete holds the module lock: create waits, then finds the module gone (409 `VersionConflictException`, existing mapping). A concurrent collection soft delete: waits, then 404. |
| Page delete | collection -> page -> collect candidate assets -> delete, flush -> `releaseAfter` (assets sorted) | Module delete locks the same pages first; whichever runs second finds the page gone (404) and touches no assets. |
| Module delete | collection -> module -> all its pages (ascending id) -> collect candidates (after the locks) -> cascade delete, flush -> `releaseAfter` | Page create, save and delete in that module are blocked on the module or page locks and then fail cleanly (above); nothing can be inserted under the module while it is deleted. |
| Cover update or create | collection (re-check) -> old and new assets, sorted | Soft delete and other cover updates hold the collection lock, so they run one at a time; the loser re-reads the new state. |
| Permanent purge (Step 20, specified now) | collection -> modules (ascending id) -> pages (ascending id) -> collect cover and page assets -> delete, flush -> `releaseAfter` | Everything below the collection is already locked, so no page can be created or saved underneath. |
| Soft delete, restore | collection only (references untouched) | Blocks and is blocked by every operation above. |
| Asset `DELETE`, sweeper stamp and purge, upload reserve and remove | asset only (`users` first for reserve and final removal, as in 12a) | They are the lowest level and never take a higher lock. |

Deadlock check: all paths are monotone in the order above; database foreign-key checks (for example PostgreSQL's `KEY SHARE` lock on the asset row when a reference is inserted) always target asset rows that the transaction already holds `FOR UPDATE`, so they add no new ordering (to be confirmed on PostgreSQL under P2).

*References (`MediaReferenceService`, the only writer of both reference forms):*
- `savePageBody(page, validatedBlocks)` (called by `createPage`/`updatePage` when `blocks != null`; metadata-only saves never call it): extract incoming ids; read the page's existing reference ids (stable, the page row is locked); **lock the union of existing and incoming ids in ascending UUID order**; validate each *incoming* asset (exists, `READY`, owned by the collection owner); diff; insert/delete; set `unreferenced_since = now` on assets that lost their last reference (any page or cover, checked after the diff) and clear it on assets that gained one. Removed assets need not be `READY`, only locked.
- `setCover(track, newAssetId)`: lock the **collection row first** (`PESSIMISTIC_WRITE` re-read), read the old cover from that locked row, then lock old and new assets sorted, validate the new one (exists, `READY`, owned by the collection owner), write `cover_asset_id`, stamp the old asset if now unreferenced, clear the stamp on the new one. Two concurrent cover updates therefore run one after the other, including the initial null-cover case.
- `releaseAfter(candidateIds)`: used by page, module and (future) collection removal. The caller collects candidate asset ids **before** the structural delete, deletes and flushes, then this locks the candidates sorted, re-checks "referenced" in a separate statement and stamps only the unreferenced ones.
- **Permanent collection purge (Step 20 will call it):** soft delete keeps the cover and page references (restore works). The purge calls `releaseCollection(track)`: collect cover id plus every page's asset ids, delete pages and the collection row, flush, then `releaseAfter`. *Correction to the review:* the FK is `tracks.cover_asset_id -> media_assets` with RESTRICT, so it protects the **asset** from deletion while a cover points at it; it can never block deleting the **collection** row. The real risk is a freed asset left unstamped, which the explicit release prevents and the sweeper's stamp-first step backstops. A test deletes a collection row that has an asset cover directly in SQL and through `releaseCollection`, and proves that deleting a still-covered asset row is refused by the FK.

*Cover contract and DTO semantics (both fields are presence-aware):*
- Both `coverAssetId` and `coverUrl` use a `Patch<T>` field type with three states: **absent** (Java `null` reference, the field was not in the JSON), **explicit null** (a marker, via a custom deserializer's `getNullValue`) and **value**. This applies to `CollectionCreate` and `CollectionUpdate`; the `@Size(max=500)` check on `coverUrl` moves into the service (the value is still run through `UrlPolicy`). A spike test comes first: absent / explicit null / value / wrong JSON type / malformed UUID through the strict creator `ObjectMapper`. If `Patch` does not hold, the fallback is reading both fields from the raw JSON node in the controller. The frontend only ever sends `coverUrl` as a string (`""` to clear) and never `null`, so nothing existing sends the states that change below.
- **Presence rule:** if both fields are present in the same request, in any state (value or explicit null), the answer is 400 and nothing is written.

| Request | `coverAssetId` | `coverUrl` |
|---|---|---|
| field absent | asset cover preserved | legacy URL preserved |
| explicit `null` | clears the asset cover (old asset stamped); the legacy URL is untouched | **400** ("Send an empty string to clear the cover URL"). Decision: `null` was previously treated as "absent", which would let a client that serialises every field silently keep a cover it meant to clear; there is exactly one way to clear, `""` |
| `""` | **400** (not a UUID) | clears the legacy URL; the asset cover is untouched |
| non-empty value | must be a canonical UUID of a `READY` asset owned by the collection owner (else 400/404 as for blocks); sets the asset cover and clears the legacy URL | must pass `UrlPolicy` (https, length <= 500); sets the URL and **clears the asset cover** through `setCover(null)`, which stamps the old asset |

- Both are never non-empty together, so `coverAssetId: null` with an existing legacy URL is a no-op for the URL. On create, `coverUrl: null` is also 400, an absent field means no cover, and `coverAssetId` is validated and applied after the collection row exists (still under the lock order, the new collection is not yet visible to anyone else).
- Public DTO: `coverUrl` is the resolved asset URL, else the legacy URL; `coverThumbUrl` is nullable. Creator DTOs carry `coverAssetId`, plus `assetId`, `width`, `height` on image blocks, and no URL (12d resolves previews through the owner route).

*Public serving:* `GET /api/public/media/{id}` and `/{id}/thumb` (already `permitAll` under `/api/public/**`). One JPQL `EXISTS` (asset `READY`) over two branches, both with `o.id = a.ownerId`: **page** (reference -> published page -> module -> collection `PUBLISHED`/`UNLISTED`, moderation `OK`, not deleted, owner `<> SUSPENDED`) and **cover** (`t.coverAssetId = a.id`, same collection conditions, a published page exists, and the collection owner equals the asset owner). The media rule is `Visibility` **and** owner-match. `Track.owner` is nullable for legacy rows and `Visibility` treats a null owner as not suspended; such a collection can never serve media because no owner can match, and the parity oracle encodes `Visibility && ownerMatches`, with a null-owner row in the matrix. Parity matrix: collection status x moderation x deleted x owner status x page status x cover with and without a published page x asset not `READY` x asset owned by another user x page moved, run against `Visibility.pageReadable` and `collectionReadable`.
- Order: parse id -> visibility (404, same body, for malformed, unknown and not servable) -> `If-None-Match` -> 304 or stream. Visibility always precedes the ETag check.
- **ETag:** strong, quoted sha256 of the variant. `If-None-Match` uses **weak comparison** (RFC 9110): `W/"x"` matches `"x"`. A small tokenizer parses `*` or a list of `[W/]"..."` tags; commas inside the quotes are part of the tag and are not split on; a malformed header counts as no match (200, not 400). `*` matches because the resource exists. A 304 carries `ETag` and `Cache-Control`. The parser is our own and unit-tested, not Spring's `checkNotModified`.
- Headers as above (`public, max-age=60`, nosniff, CSP sandbox, `Content-Length`, no `Content-Disposition`, no ranges).

*Delete and orphan cleanup:* `DELETE /api/media/{id}` uses `CurrentUser.require()`, so anonymous and suspended callers get **401**; non-owner, admin and unknown ids get 404. Lock asset -> re-check references in a separate statement -> `MEDIA_IN_USE` 409 (up to 20 usages and the total; needs `CodedConflictException` to carry a payload) / `MEDIA_NOT_READY` 409 / `DELETING` repeat 204 / mark `DELETING`, commit, inline `finalizeDeletion`, 204 even if storage fails. Sweeper, in this order: (1) **stamp** and (2) **purge** are both lock-and-recheck operations, and (3) is the existing `DELETING` pass.
- *Invariant, maintained by every reference writer under the asset lock:* a referenced asset has `unreferenced_since IS NULL`; an unreferenced asset has NULL (orphaned, not yet stamped) or the time it became unreferenced. Only a writer holding the asset lock changes the stamp.
- **(1) Stamp**, per candidate (the candidate query is advisory): in its own transaction lock the asset row `FOR UPDATE` (fresh read); require `READY` **and** `unreferenced_since IS NULL` as read under the lock; re-check "referenced" in a **separate statement**; only then write `unreferenced_since = <clock read after the lock was acquired>`, never a time observed before the lock. It never overwrites a non-NULL stamp. It is not purged in the same pass.
- **(2) Purge**, per candidate: lock the row; re-read `status`, `unreferenced_since` and "referenced" **under the lock**; require `READY`, unreferenced, and `unreferenced_since` (as re-read, not as selected) older than 24 h; then `DELETING`. Re-reading the stamp matters: if a creator attached and later detached the asset between selection and the lock, the stamp is new and the asset is not purged.
- *How this serialises:* page save (union of existing and incoming ids) and cover change (old and new asset) lock every asset whose reference state they change, insert or delete the reference, and set or clear the stamp in the same transaction. The sweeper takes the same row lock. If the sweeper locks first it sees no reference and stamps with the current time (the full 24 h grace starts then); the creator then waits, attaches and clears the stamp. If the creator locks first, the sweeper waits and then sees the reference and does nothing. Neither can write a timestamp based on a stale observation, so an asset that was attached and detached cannot be purged earlier than 24 h after the detach. References removed by a database cascade (JPA delete of pages without `releaseAfter`) leave the stamp NULL, which step (1) later stamps with a fresh time. Candidate queries are advisory (`NOT EXISTS`), the check under the lock is authoritative, batches use an id cursor, every step is idempotent and forward-only.

It runs after every media/collection API test and as a read-only sweeper diagnostic that logs mismatches. It repairs nothing.

- **P7 result (AWS SDK v2 2.57.12, observed on the wire against a recording server, plain HTTP; `S3MediaStorageSdkBehaviourTest`).** (1) The SDK does **not** buffer a `RequestBody.fromInputStream` stream: no byte has been read when the request headers arrive. (2) An **overlong** stream is silently truncated to the declared `Content-Length` and the `PutObject` **succeeds**: a committed object holding only a prefix of the data, which breaks the `MediaStorage` contract. (3) A **short** stream is noticed only after the request is on the wire, and as `IllegalStateException`, not an `SdkException`. (4) Over plain HTTP the SDK uses `aws-chunked` with a signed payload. Consequence: `put` reads the stream into a buffer of exactly `length` bytes plus a one-byte probe for excess **before any request is made** (an endless stream is read at most `length + 1` bytes), then sends a replayable `fromBytes` body with an explicit `x-amz-checksum-sha256` that S3 verifies server-side. A bad stream therefore cannot create, truncate or replace an object. Cost: heap per call is bounded by `media.s3.max-object-size` (default 32 MB, must be at least `media.max-bytes`); larger objects are refused with `IllegalArgumentException`. Multipart upload is **not implemented**, so a single `PutObject` is the only write and there is **no multipart upload to abandon**; the MinIO test asserts `listMultipartUploads` stays empty after success, short, long, failing and killed-client uploads. The SDK tests are tripwires: re-check `S3MediaStorage`'s Javadoc when the SDK version changes. Not measured: HTTPS behaviour (the SDK then uses an unsigned payload) and real AWS; both belong to P3/P8.
- **Checksums:** the client sets request and response checksum calculation to `WHEN_REQUIRED`, because the SDK default of a trailing CRC32 in `aws-chunked` is rejected by older MinIO and some other S3-compatible stores. Integrity relies on the explicit SHA-256 header.
- **Backend selection (`MediaConfig.create`):** `local` or `s3` only; a blank or unknown value fails startup (no fallback to disk). `local` under a profile named `prod` or `production` fails startup with a message naming the fix. `s3` needs `media.s3.bucket` and a `HeadBucket` at startup (missing or unreachable bucket stops the application, rather than the first upload). - **Semantics:** `delete` is idempotent (S3 answers 204 for a missing key); `open` maps a missing key to `NoSuchFileException`; `exists` never reports an error as "absent" (a 5xx or a missing bucket is an `IOException`); overwrite is atomic in S3 and a failed overwrite keeps the old object.
